# What Transfers Across Cities? — artifact

Code, data conversions and result files for the ICDE 2027 EAB paper
*What Transfers Across Cities? An Experimental Analysis of Zero-Shot Route Generation*.

Every number, table and figure in the paper is produced by `src/paper_artifacts.py` from the JSON files in
`src/results/` (LaTeX macros in `numbers.tex`; no number in the paper is typed by hand). Running
`src/paper_artifacts.py` on the shipped results reproduces the paper's `numbers.tex` and tables byte for byte.

## 1. Environment
- Conda environments in `env/`: `gtg.yml` (all our experiments; Python 3.9, PyTorch 2.4/CUDA 11.8,
  torch_geometric 2.3.1, scikit-learn), `gtgp2.yml` (GTG official code; needs `graph-tool`, imported before torch),
  `hoser.yml` (HOSER official code; adds haversine, loguru, tensorboard, cmake, and the PyPI `mpich` wheel used
  to build KaHIP).
- Hardware used: 20 CPU cores, 2x RTX 4090 (24 GB), 219 GB RAM.
- Edit paths in `config.sh` if needed (`source config.sh`; every script in `src/` does this itself).

## 4. Conventions
- All shortest paths use RAW segment lengths (`src/routing.py`); free-flow time = length / class speed;
  class-weighted length = length x class factor (`src/e4.py`); edge weight (cost[u] + cost[v]) / 2 on the
  segment graph (same shortest paths as summing segment costs).
- Primary metric: length-weighted LCS route F1 (`CC_F1=length`); `CC_F1=count` gives the count-based variant.
- Hausdorff distance: `routing.hausdorff_metric` (haversine, R = 6378 km), the formula of the GTG/HOSER evaluation code.

## 5. Reproduction
`src/reproduce_all.sh` runs everything in order: MAP6 candidate pools -> E4-E10 (`run_len.sh`, `e10.py`) ->
recursive logit (`rl2.py`, `rl_map6_len.py`) -> GTG (official training, generation, evaluation, repeat runs,
in-city runs `run_gtg_samecity.sh`, target-label check `gtg_label_check.py`) ->
HOSER (official training with fallback, generation, evaluation, few-shot) -> extras (`bok_flow.py`,
`exact_sp_control.py`, timing) -> statistics and analyses on CPU (`e11_stats.py`, `e11b_gtg_incity.py`,
`e12_sources.py`, `e13_dist.py`, `e14_kcand.py`, `e15_kcand_logit.py`, `e16_temporal.py`, `e17_observed_ti.py`,
`e17b_inset_ti.py`, `e17c_inset_detail.py`, `e19_temporal_counts.py`, `e20_param_tests.py`, `e20b_robust_tests.py`, `e21_why.py`) -> `paper_artifacts.py`. GTG training takes about one day per direction (about three
from Beijing); everything else runs in hours on the hardware above.

**Re-scoring the deep generators without retraining.** The routes generated by GTG (all runs, 10^5 test
queries per direction: `src/results/gtg/**/gen_*.csv.gz`) and by HOSER (full data, few-shot and the training-budget
check, 10^4 evaluation queries: `routes/hoser/`) are included. `src/unpack_routes.sh` unpacks them to where the
evaluation scripts read them; then run `gtg_ids.py`, `hoser_ids.py`, `hoser_fs_ids.py`, the MAP6 pools (`run_len.sh`)
and `gtg_eval.py`, `hoser_eval.py`, `hoser_fs_eval.py`, `hoser_fs_budget_eval.py`. The routes are sequences of segment
ids of the GTG and HOSER releases and are derived from those datasets; use them under the datasets' terms.

## 7. Disclosures
- The post-hoc rule of RQ2 (Sec. V-B) uses equal weights, chosen after inspecting the estimated training coefficients of all five cities and not tuned; it is a diagnostic. `E21_F` gives the source-selected rule: signs and discrete weights chosen on source training trips only (242 rules with weights 0, 1, 2; it still learns from source data): leave-one-city-out and, for the GTG comparison, on GTG's single source. The 66-point weight grid is scored on test trips as a post-hoc diagnostic only.
- GTG and HOSER use the hyper-parameters of their repositories; nothing was tuned on target data.
- Timing numbers come from runs on one shared machine; they are indicative.
- GTG's official code sets no random seed; we report three runs for two directions.
- GTG's official training also reads the target city's segment travel-time labels (`traj/train_label.csv`), which
  only decide which target subgraph samples are kept; `gtg_label_check.py` shows that none is dropped on our data.

## 8. Observed-choice check in detail (E17c, `E17c_inset_detail_*_len.json`)
Covered trips: test trips whose observed route is one of their MAP6 candidates, so the label is the observed choice
(RQ2). Models are fitted on covered training trips (in-city; pooled other four cities). CIs: 2,000 bootstrap resamples
of OD pairs. On covered trips that are not shortest paths, TI is unstable (the in-city model is fitted mostly on
shortest-path choices), so we compare top-1 hit rates there (CIs: 2,000 bootstrap resamples of OD pairs);
per-source TIs are in the JSON.

## 9. Temporal split details (E16, E19)
Cutoff = start of the day that contains the 75% quantile of training start times. E16 fits the in-city references
on training trips before the cutoff; E19 calibrates the count model (C2, sensors on 10% of the segments, the three
E8 placements) on counts of the earlier test trips and scores the flows of the later test trips. Only the calibrated
parameters are carried over; later flows are predicted for the later trips' own ODs.
